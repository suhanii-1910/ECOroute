6. Derived Views (not base tables)
View
Definition
Purpose
V_ROUTE_WEIGHT
SELECT r.route_id, SUM(rw.estimated_quantity) AS total_estimated_weight, SUM(rw.actual_quantity) AS total_actual_weight FROM ROUTE r LEFT JOIN ROUTE_STOP rs ON rs.route_id = r.route_id LEFT JOIN REQUEST_WASTE rw ON rw.request_id = rs.request_id GROUP BY r.route_id
Route totals (kg) are derived and are never stored as columns of ROUTE.
V_PICKUP_REQUEST_ZONE
SELECT pr.request_id, pr.generator_id, wg.zone_id FROM PICKUP_REQUEST pr JOIN WASTE_GENERATOR wg ON wg.generator_id = pr.generator_id
PICKUP_REQUEST has no zone_id; the zone is derived through generator → zone.

Notes
net_disposed_weight_kg is a derived attribute (dashed ellipse in the diagrams): it is defined as gross_weight_kg - tare_weight_kg and implemented as a generated column.
ROUTE_STOP.request_id NOT NULL + UNIQUE realises the 1 : 0..1 scheduled_in relationship with total participation of the stop side.
FACILITY_ACCEPTED_WASTE is the authorization matrix: application logic must insert a DISPOSAL_RECORD only at a facility that accepts every category loaded on the route.
Specialization mapping uses one table per subtype with PK+FK; discriminators generator_type and facility_type carry the CHECK constraints.
Both EER specializations (WASTE_GENERATOR → HOSPITAL / HOUSING_SOCIETY / FACTORY and DISPOSAL_FACILITY → RECYCLING_PLANT / PROCESSING_PLANT / HAZARDOUS_DISPOSAL_SITE) are disjoint and partial: a supertype row has at most one subtype row, and may have none (generator_type HOTEL, SCHOOL, RESTAURANT, OFFICE, OTHER and facility_type LANDFILL have no subtype table).
Total participation shown by double lines (route must have at least one ROUTE_STOP; pickup request must have at least one REQUEST_WASTE row) is enforced in application logic, because SQL foreign keys can only enforce the child-to-parent direction.
Subtype FKs (PK+FK to the supertype) use ON DELETE CASCADE so a subtype row never outlives its supertype row.
Units: every weight and quantity is in kilograms except DISPOSAL_FACILITY.capacity_tonnes_per_day, which is in tonnes per day. Multiply by 1000 before comparing it with kg values.
Nullability: every column states NULL or NOT NULL explicitly. address (generators and facilities), preferred_pickup_date, facility latitude/longitude, is_active, created_date, unloading_timestamp, processing_rate_per_kg and DISPOSAL_RECORD.status are NOT NULL; contact_person, phone, email, generator latitude/longitude, descriptions, remarks, completion_date, actual_quantity, arrival_time, completion_time and the optional subtype attributes are NULL.
Route weights: ROUTE stores no total_estimated_weight or total_actual_weight; they are derived through V_ROUTE_WEIGHT (section 6).
Platform: MySQL 8.0.16 or later is required, because earlier versions parse CHECK constraints but do not enforce them. The USER role rule is written as CHECK ((role = 'GENERATOR' AND generator_id IS NOT NULL) OR (role <> 'GENERATOR' AND generator_id IS NULL)). USER should be quoted with backticks in raw SQL.

7. Implementation Clarifications and Integrity Addendum
This addendum supplements the approved schema and preserves all 18 relations, all existing columns, keys, CHECK lists, foreign keys, delete rules, views and integrity rules. It clarifies implementation and validation; it does not silently replace the approved relational design.
7.1 Additional CHECK constraints to implement
Add the following domain checks to the SQL implementation, subject to the team’s approval of these integrity rules. They do not require removing or renaming any existing attribute:
REQUEST_WASTE.estimated_quantity >= 0.
REQUEST_WASTE.actual_quantity IS NULL OR actual_quantity >= 0.
VEHICLE.capacity_kg > 0.
DISPOSAL_FACILITY.capacity_tonnes_per_day > 0.
FACILITY_ACCEPTED_WASTE.processing_rate_per_kg >= 0.
ROUTE_STOP.stop_sequence > 0.
DISPOSAL_RECORD.gross_weight_kg >= 0 and tare_weight_kg >= 0.
DISPOSAL_RECORD.gross_weight_kg >= tare_weight_kg.
Use enforced CHECK constraints on MySQL 8.0.16+. Keep actual_quantity nullable. The generated expression must be gross_weight_kg - tare_weight_kg using the ordinary ASCII hyphen-minus; net_disposed_weight_kg is generated and must not be supplied by INSERT or UPDATE statements.
7.2 Derived view interpretation
V_ROUTE_WEIGHT uses the ROUTE → ROUTE_STOP → REQUEST_WASTE path. With ROUTE_STOP.request_id UNIQUE, this join does not inherently multiply request rows across routes. Ensure quantities across category rows are non-overlapping amounts before summing them.
SUM(actual_quantity) ignores NULL. A NULL actual_quantity means “not recorded,” not zero. Any report that displays total_actual_weight must also communicate whether all applicable actual quantities have been recorded; otherwise label the sum as a partial recorded subtotal.
Keep LEFT JOIN semantics if routes with no stops must appear. Decide whether a route with no matching waste rows should display NULL or 0 and use that convention consistently.
7.3 Subtype specialization enforcement
Implement all six BEFORE INSERT subtype triggers: HOSPITAL, HOUSING_SOCIETY, FACTORY, RECYCLING_PLANT, PROCESSING_PLANT and HAZARDOUS_DISPOSAL_SITE. Each checks that the discriminator matches and that the supertype ID is absent from the other subtype tables.
Implement both BEFORE UPDATE discriminator triggers on WASTE_GENERATOR.generator_type and DISPOSAL_FACILITY.facility_type. Reject changes that conflict with existing subtype rows. Define a policy for updates to subtype PK/FK IDs; a safe project rule is to disallow changing those IDs after insertion.
7.4 Disposal authorization and capacity
sp_record_disposal validates facility existence and active status, route/facility lifecycle eligibility, acceptance of every category loaded on the route, non-negative weights, gross >= tare, unique receipt number, and daily capacity.
Daily capacity is the sum of net_disposed_weight_kg for the facility and unloading calendar day, compared with capacity_tonnes_per_day × 1000. State the calendar-day/timezone convention.
Run the capacity check and insert atomically in a transaction, locking a stable facility row (for example, SELECT ... FOR UPDATE) so concurrent disposal attempts cannot both pass based on the same prior total. On any validation failure, roll back and signal a clear error.
The schema permits multiple DISPOSAL_RECORD rows per route. Retain that unless the team formally revises the schema; document whether a route can unload more than once. Do not assume route actual collected weight equals one disposal record’s net weight.
7.5 Cross-table rules not guaranteed by these FKs
Before route assignment, validate that the request generator’s zone matches ROUTE.zone_id.
Enforce the documented total-participation rules in the controlled workflow: each eligible/submitted pickup request must have at least one REQUEST_WASTE row, and a route must have at least one ROUTE_STOP before dispatch. Foreign keys alone do not enforce these rules.
Define and validate the relationship between preferred_pickup_date and ROUTE.route_date, plus allowed status transitions for requests, stops and routes.
Define how BIOMEDICAL/high-hazard categories map to facility authorization. FACILITY_ACCEPTED_WASTE proves category acceptance only; where subtype clearance fields are intended to represent regulatory authorization, validate that policy in sp_record_disposal.
The USER role/generator_id CHECK is not a complete authorization system. Apply role permissions in the Java application and use appropriately restricted database credentials.
7.6 SQL and test notes
Quote USER as `USER` in SQL. Use MySQL 8.0.16 or later and verify the server version.
Test boundary and rejection cases: negative quantities/weights, zero capacities, gross < tare, stop_sequence <= 0, NULL actual quantities, empty routes, requests without waste rows, cross-zone assignments, invalid status transitions, duplicate receipt numbers, exact-capacity and over-capacity disposal, and concurrent disposal attempts where feasible.
All existing relations, columns, keys, delete rules, two views, specialization rules and disposal rules remain in scope. This addendum is additive; no existing requirement is waived.
