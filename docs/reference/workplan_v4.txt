What changed since the original plan
The original plan covered 12 relations. The corrected schema has 18 and replaces the earlier disposal-site design, so the DBMS work changes in the areas below. Version 2 of this plan (15 relations, DISPOSAL_SITE, user subtype tables) is superseded.

1. Common team rules
Treat the corrected relational schema as the database source of truth. Do not silently rename tables/columns or alter key relationships.
The core project is an academic prototype. GPS/live tracking, Google Maps, AI/ML, IoT weighing, mobile apps, commercial route optimization and real-time fleet tracking remain outside the core scope.
Vehicle assignment is a greedy capacity-constrained heuristic; nearest-neighbor is a routing heuristic; disposal-facility selection is a nearest-suitable-facility heuristic (active, accepts every category on the route, enough daily capacity). None is to be described as globally optimal.
Finish the P0 end-to-end workflow before peripheral syllabus demonstrations.
Use Git with small descriptive commits. Coordinate before changing shared classes, interfaces or SQL.
Every member must understand and be able to explain their own contribution during individual evaluation.
2. Final database baseline
The corrected design contains 18 relations: ZONE, WASTE_GENERATOR, USER, WASTE_CATEGORY, VEHICLE, PICKUP_REQUEST, REQUEST_WASTE, ROUTE, ROUTE_STOP; DISPOSAL_FACILITY, FACILITY_ACCEPTED_WASTE, DISPOSAL_RECORD; and the subtypes HOSPITAL, HOUSING_SOCIETY, FACTORY, RECYCLING_PLANT, PROCESSING_PLANT, HAZARDOUS_DISPOSAL_SITE.
Area
Rule to preserve
Generator zone
WASTE_GENERATOR.zone_id is a mandatory FK to ZONE (RESTRICT).
Request zone
PICKUP_REQUEST has no zone_id; derive it through generator → zone (V_PICKUP_REQUEST_ZONE).
Users
One USER table; username UNIQUE; role CHECK (GENERATOR, ADMIN, OPERATOR, DRIVER); generator_id is NULL unless role = GENERATOR, in which case it is required.
Route
ROUTE references one VEHICLE and one ZONE (both NOT NULL, RESTRICT). status is CHECK-limited (PLANNED, IN_PROGRESS, DISPATCHED_TO_DISPOSAL, COMPLETED, CANCELLED). Route total weights are derived, never stored.
Route stop
ROUTE_STOP has stop_id PK, request_id NOT NULL UNIQUE (RESTRICT) and UNIQUE(route_id, stop_sequence); route_id is CASCADE.
Request waste
REQUEST_WASTE has composite PK (request_id, category_id), estimated_quantity NOT NULL and nullable actual_quantity; request_id CASCADE, category_id RESTRICT.
Waste category
category_name UNIQUE; hazard_level NOT NULL, default LOW, CHECK (LOW, MEDIUM, HIGH, BIOMEDICAL).
Generator subtypes
HOSPITAL, HOUSING_SOCIETY and FACTORY use generator_id as PK/FK (CASCADE); disjoint and partial; generator_type is the discriminator.
Disposal facility
DISPOSAL_FACILITY: facility_name UNIQUE; facility_type CHECK (RECYCLING_PLANT, PROCESSING_PLANT, HAZARDOUS_DISPOSAL_SITE, LANDFILL); zone_id NOT NULL (RESTRICT); capacity_tonnes_per_day is in tonnes.
Facility subtypes
RECYCLING_PLANT, PROCESSING_PLANT and HAZARDOUS_DISPOSAL_SITE use facility_id as PK/FK (CASCADE); disjoint and partial; LANDFILL has no subtype table.
Accepted waste
FACILITY_ACCEPTED_WASTE has composite PK (facility_id, category_id); facility_id CASCADE, category_id RESTRICT.
Disposal record
DISPOSAL_RECORD: route_id and facility_id RESTRICT; receipt_number UNIQUE; net_disposed_weight_kg generated (gross − tare); status CHECK (VERIFIED, DISCREPANCY, REJECTED).
Vehicle home zone
VEHICLE.assigned_zone_id is nullable and uses SET NULL on zone deletion.
Delete behavior
RESTRICT by default. CASCADE: ROUTE_STOP.route_id, REQUEST_WASTE.request_id, FACILITY_ACCEPTED_WASTE.facility_id and all six subtype FKs. SET NULL: VEHICLE.assigned_zone_id only.
Units
All weights and quantities are kg, except DISPOSAL_FACILITY.capacity_tonnes_per_day (tonnes per day; multiply by 1000 to compare).
Participation
A route should have at least one ROUTE_STOP and a pickup request at least one REQUEST_WASTE row; this is enforced in application/procedure logic, not by foreign keys.
Views
V_ROUTE_WEIGHT and V_PICKUP_REQUEST_ZONE are derived views, not base tables.

3. End-to-end workflow
Create a pickup request with category, estimated quantity and preferred date.
Persist the request in MySQL through JDBC.
Review pending requests.
Group requests by predefined zone.
Run greedy capacity-constrained vehicle assignment.
Generate route stops and nearest-neighbor sequence.
Collection staff views the route and completes stops.
Actual quantity and statuses are updated.
When the stops are complete or the vehicle is full, select the nearest suitable DISPOSAL_FACILITY (active, accepts every category on the route, enough daily capacity) and record the unloading through sp_record_disposal, which creates the DISPOSAL_RECORD with gross weight, tare weight and receipt number; net weight is generated.
Reports show collection volume, utilization, status, estimated-vs-actual results and disposal records per facility.
Demonstrate SQL queries, joins, aggregates, procedures, functions, triggers and relevant Java syllabus components.

5. Exact database procedure
	•	Create the MySQL database (MySQL 8.0.16 or later so CHECK constraints are enforced) and agree the name/configuration with the team.
	•	Create ZONE and WASTE_CATEGORY first (zone_name and category_name UNIQUE; hazard_level NOT NULL DEFAULT LOW with its CHECK).
	•	Create WASTE_GENERATOR with mandatory zone_id FK and generator_type with its CHECK list.
	•	Create HOSPITAL, HOUSING_SOCIETY and FACTORY after WASTE_GENERATOR, each with generator_id as PK/FK ON DELETE CASCADE.
	•	Create USER (quoted as `USER`) with UNIQUE username, role CHECK, nullable generator_id FK and the role/generator_id CHECK.
	•	Create VEHICLE with UNIQUE vehicle_number, status CHECK and nullable assigned_zone_id FK (SET NULL).
	•	Create DISPOSAL_FACILITY (zone_id FK RESTRICT, facility_type CHECK, UNIQUE facility_name), then RECYCLING_PLANT, PROCESSING_PLANT and HAZARDOUS_DISPOSAL_SITE (PK/FK CASCADE), then FACILITY_ACCEPTED_WASTE with composite PK.
	•	Create ROUTE after VEHICLE and ZONE; vehicle_id and zone_id NOT NULL; status CHECK; no stored weight columns.
	•	Create PICKUP_REQUEST after WASTE_GENERATOR with status CHECK and default PENDING.
	•	Create ROUTE_STOP after ROUTE and PICKUP_REQUEST; request_id NOT NULL UNIQUE, UNIQUE(route_id, stop_sequence), route_id CASCADE.
	•	Create REQUEST_WASTE after PICKUP_REQUEST and WASTE_CATEGORY with composite PK (request_id, category_id).
	•	Create DISPOSAL_RECORD after ROUTE and DISPOSAL_FACILITY with the generated net_disposed_weight_kg column, UNIQUE receipt_number and RESTRICT FKs.
	•	Insert representative seed data for every table, including one user per role, one facility per subtype plus a LANDFILL, accepted-waste rows and disposal records.
	•	Create V_ROUTE_WEIGHT from REQUEST_WASTE through ROUTE_STOP and V_PICKUP_REQUEST_ZONE through generator → zone.
	•	Prepare JOIN, aggregate, GROUP BY/HAVING, disposal and estimated-vs-actual report queries.
	•	Create the procedures: a zone collection summary or controlled status update, and sp_record_disposal with its authorization and capacity checks.
	•	Create a function such as route utilization percentage; guard against missing vehicle/zero capacity.
	•	Create the subtype consistency triggers, documenting event, timing, rule and expected result for each.
	•	Rebuild the database from a clean script and confirm it works without manual fixes.

7. Procedure/function/trigger guidance
Procedure candidate: get_zone_collection_summary(zone_id, target_date).
Procedure candidate: update_pickup_status(request_id, new_status), with validation if needed.
Procedure (required by the schema): sp_record_disposal(route_id, facility_id, gross_weight_kg, tare_weight_kg, receipt_number). It checks that the facility is active, that FACILITY_ACCEPTED_WASTE covers every category loaded on the route, and that the day's net weight stays within capacity_tonnes_per_day × 1000, then inserts the DISPOSAL_RECORD.
Function candidate: route_utilization(route_id) = derived route estimated weight / assigned vehicle capacity × 100; return NULL/0 safely when the vehicle is missing or capacity is zero.
Trigger set (justified by the schema, not by marks): BEFORE INSERT on HOSPITAL, HOUSING_SOCIETY, FACTORY, RECYCLING_PLANT, PROCESSING_PLANT and HAZARDOUS_DISPOSAL_SITE (discriminator must match, subtype tables must stay disjoint) and BEFORE UPDATE on generator_type and facility_type. Document at least one fully; implement all six subtype INSERT triggers and both discriminator UPDATE triggers; none of these triggers is optional.
Do not store ROUTE total_estimated_weight or total_actual_weight as base columns; they are derived through V_ROUTE_WEIGHT. DISPOSAL_RECORD.net_disposed_weight_kg is the one stored generated column.

13. Required implementation clarifications and corrections
This section supplements the approved 18-relation design. It does not remove relations, columns, views, procedures, functions, triggers, test cases or Java handoff requirements. Keep the approved names, keys, relationships and delete rules unless the team formally approves a schema revision.
13.1 Numeric and generated-column integrity
Add CHECK constraints, where supported by the approved schema and MySQL 8.0.16+, requiring non-negative estimated_quantity, actual_quantity when non-NULL, gross_weight_kg, tare_weight_kg, processing_rate_per_kg, and non-negative capacities. Require vehicle capacity_kg and facility capacity_tonnes_per_day to be greater than zero. Require stop_sequence > 0.
For DISPOSAL_RECORD, require gross_weight_kg >= tare_weight_kg >= 0. Define net_disposed_weight_kg as gross_weight_kg - tare_weight_kg using the ordinary SQL hyphen-minus character, not a typographic minus. Do not supply the generated column in INSERT statements.
The corrected schema currently makes actual_quantity nullable. Preserve that choice, but interpret NULL as “not yet recorded,” not zero. V_ROUTE_WEIGHT must expose whether actual quantities are complete (for example, an additional completeness/count indicator or a separate reporting query). Do not present SUM(actual_quantity) as a complete route actual total if any relevant actual_quantity is NULL. SQL SUM ignores NULL values.
13.2 V_ROUTE_WEIGHT semantics
Use the documented join path ROUTE → ROUTE_STOP → REQUEST_WASTE and group by route_id. ROUTE_STOP.request_id is UNIQUE, so the join does not inherently duplicate a request across routes. Confirm that each REQUEST_WASTE row represents a distinct, non-overlapping quantity in kg; do not add category quantities if the application stores overlapping totals.
Keep routes with no stops in the view by retaining LEFT JOINs. Such routes should show zero or NULL according to the chosen reporting convention; document the convention and use COALESCE only if zero is semantically appropriate. Actual totals remain incomplete until all applicable actual quantities are recorded.
13.3 Required subtype trigger coverage
Implement BEFORE INSERT triggers for HOSPITAL, HOUSING_SOCIETY, FACTORY, RECYCLING_PLANT, PROCESSING_PLANT and HAZARDOUS_DISPOSAL_SITE. Each must verify the supertype discriminator and check the other subtype tables to enforce disjointness.
Implement BEFORE UPDATE triggers on WASTE_GENERATOR.generator_type and DISPOSAL_FACILITY.facility_type. Reject a discriminator change that would disagree with an existing subtype row. Define and test a policy for changing subtype primary-key/foreign-key IDs; simplest is to prohibit changing them after insertion.
Test both successful and rejected inserts, attempts to insert a second subtype for the same supertype, and discriminator changes both to a matching and non-matching value. Do not describe a trigger as enforcing a rule unless its test demonstrates that rule.
13.4 Disposal procedure: validation, lifecycle and concurrency
sp_record_disposal must reject negative weights, gross weight below tare weight, duplicate receipt numbers, inactive facilities, facilities that do not accept every category on the route, and facility/day capacity overflow. Validate that the route and facility exist and that the route is in a permitted lifecycle status before recording disposal.
Perform the capacity check and insert in one transaction. Serialize competing capacity checks for the same facility/day (for example, lock the stable DISPOSAL_FACILITY row with SELECT ... FOR UPDATE before reading that day’s records and inserting). Roll back and signal a clear SQL error if validation fails. A simple check followed by an unprotected insert is vulnerable to concurrent overbooking.
Capacity is the sum of net_disposed_weight_kg for the facility and calendar date of unloading_timestamp, compared with capacity_tonnes_per_day × 1000. State the timezone/calendar-day convention used by the application.
Define the allowed number of DISPOSAL_RECORD rows per route. The current schema permits multiple records for one route. Preserve that capability unless the team formally changes the schema; document whether multiple unloadings are allowed and how each unloading’s measured net weight is interpreted.
Do not assume a route’s collected actual weight must equal a disposal record’s net weight. Partial collection, multiple unloadings, tare/gross measurement differences and unrecorded actual quantities can create differences. Report the values separately and flag discrepancies rather than silently forcing equality.
13.5 Cross-table and lifecycle rules
Before assigning a request to a route, validate that the request generator’s zone matches ROUTE.zone_id. The existing foreign keys cannot enforce this cross-table condition by themselves.
Before a request is submitted/eligible for assignment, require at least one REQUEST_WASTE row. Before a route is dispatched, require at least one ROUTE_STOP. These total-participation rules are not enforced by the current foreign keys; enforce them in the controlled application workflow or a suitable transaction/procedure and test rejection cases.
Define how preferred_pickup_date relates to ROUTE.route_date, and enforce the chosen policy in assignment logic. Also define valid status transitions for PICKUP_REQUEST, ROUTE_STOP and ROUTE so impossible transitions (such as completing a cancelled request) are rejected.
Define hazardous/biomedical authorization explicitly. The current facility accepted-waste matrix determines accepted categories, but does not by itself prove that a facility has the required regulatory authorization. If the project models authorization through facility subtype and clearance fields, validate that rule in sp_record_disposal and document the mapping; do not invent a new table without team approval.
The USER role/generator_id CHECK enforces the documented relationship, not full authorization. Apply role-based checks in Java and restrict database credentials appropriately. Quote the table as `USER` in SQL.
13.6 SQL portability and verification
Use MySQL 8.0.16 or later and verify the exact server version in the evidence. CHECK constraints were not enforced in older MySQL releases.
Use regular ASCII hyphen-minus in SQL arithmetic. Keep capacity units explicit: quantities and weights are kg; capacity_tonnes_per_day is tonnes/day and must be multiplied by 1000 for comparison.
Add test cases for negative quantities/weights, zero or negative capacities, gross < tare, stop_sequence <= 0, NULL actual quantities, empty routes, requests without waste rows, cross-zone assignment, invalid status transitions, duplicate receipts, facility/day capacity boundaries, and two concurrent disposal attempts if concurrency can be demonstrated.
For any rule implemented in Java rather than SQL, identify it explicitly in docs/db_test_cases.md and demonstrate both accepted and rejected cases. Application checks do not replace required declarative constraints or the required subtype triggers.
